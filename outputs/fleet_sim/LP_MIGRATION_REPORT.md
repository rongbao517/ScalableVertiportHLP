# 再平衡机制迁移报告:从 Tier0(净流入启发式)到滚动定位LP

2026-07-23。本报告完整记录一次调查的全过程:从一个真实bug的发现,到最终用滚动定位LP
重新解决"三布局是否可行"这个最初问题。所有数字均可在 `outputs/fleet_sim/` 下对应的
`time_step_summary_*.csv` / `eqsearch_trajectory_*.csv` / `rebalance_log_*.csv` 中复核,
无手工誊抄。

## 一、时间线

1. **v1(原始冻结基线)**——三布局(Oracle/mode-choice/threshold, fleet=7500)在旧版
   Tier0(净流入EMA启发式)下全部收敛且R\*≥95%,mode-choice被判定为最优布局。
2. **发现bug**——`task_assignment.py`把"取整噪声"和"真实缺车"混在一起喂给反应式
   再平衡(Tier1),导致虚假信号触发误调度(grid 433等站点)。
3. **修复采纳(v2)**——新增`unmet_for_rebalancing`信号,排除取整噪声,只保留真实缺口。
   全量重跑三布局+敏感性场景后,**R\*全线下降、全部跌破95%**,包括原本安全的fleet=12000。
4. **两轮诊断**——确认修复本身没有过宽(删除的95%都是纯噪声),确认fleet=12000上不去
   95%是空间/时间错配(71.8%车队闲置),不是容量不足。
5. **启发式调参触顶**——两轮敏感性分析证明Tier0参数空间天花板很低(≤0.2pp),且暴露
   了783/928/925这类"车多但自己也缺"枢纽站被误伤的问题;自身缺口过滤器验证有效但
   治标不治本(783是尖峰型缺口,反应式过滤器防不住)。
6. **重新定位为优化问题**——离线全知LP证明理论上限是100%(vs当时81-82%的原始口径,
   官方口径下Tier0 baseline实为94.74%),确认问题是"车该放哪"而非"信号该信谁"。
7. **滚动定位LP开发与验证**——H=4/8/12测试、5场景+反向初始分布稳健性验证、三项
   运营指标(R\*、空载里程、反应式调度量)一致改进、H=8确定为最终工程配置。
8. **LP正式接入完整均衡搜索**——三布局在fleet=7500下用LP重新收敛,**全部重新
   越过95%**,但布局排名发生反转,已在H=12下复核确认为稳健发现。

## 二、三布局完整对比:v1(原始) → v2(修复后Tier0) → v3(修复后+LP)

| 布局 | D\*(v1,万) | R\*(v1) | D\*(v2,万) | R\*(v2) | D\*(v3,万) | **R\*(v3)** | v3是否可行(≥95%) |
|---|---|---|---|---|---|---|---|
| Oracle基准 | 353.5 | 96.40% | 344.02 | 93.61% | 354.12 | **96.57%** | ✅ |
| mode-choice候选 | 357.9 | 96.84% | 346.96 | 93.80% | 355.38 | **95.99%** | ✅ |
| threshold对照 | 347.3 | 96.44% | 337.44 | 93.08% | 352.60 | **96.81%** | ✅ |

**关键叙事**:v1→v2的R\*下降(96.4-96.8% → 93.1-93.8%)是修复取整噪声bug的真实代价
(旧逻辑靠虚假信号"额外"调度出来的服务率,本就不该算数)。v2→v3的R\*回升
(93.1-93.8% → 96.0-96.8%)不是"运气变好",是滚动LP真正解决了再平衡机制本身的问题——
且v3阶段D\*普遍比v2高(服务变好吸引了更多需求,系统在更高需求水平上重新找到均衡),
R\*依然回升,证明改善是真实的,没有被"需求更低所以更容易达标"稀释。

**布局排名反转**:
- v1/Tier0下:mode-choice > Oracle > threshold(mode-choice是"最优"布局)
- v3/LP下:**threshold > Oracle > mode-choice**(threshold变最优,mode-choice变最差)
- 已在H=12下复核,排名反转在两个H配置下都成立,是稳健发现,不是H=8的偶然产物。

## 三、诊断与验证过程摘要

| 阶段 | 核心发现 |
|---|---|
| 诊断一(修复是否过宽) | 94.9%的被删信号是纯取整噪声(real_gap≈0);真实缺口(5.2%的site-bin组合)从未被误删,只是叠加在其上的噪声被移除 |
| 诊断二(容量 vs 错配) | fleet=12000场景:71.8%车队时间闲置;P_mismatch=80%;拒单瞬间平均7923.6辆车闲置在别处(V_stranded) |
| 启发式敏感性(round1/2) | gain/threshold在max_drain约束下是死参数;max_drain是唯一有效杠杆但天花板≤0.35pp;783站点被drain越狠自身缺口越大 |
| 自身缺口过滤器 | 时序验证正确(只用决策时已记录的缺口,不引入未来信息);783因缺口集中于偶发尖峰(仅14.4%的bin有真实缺口),反应式过滤器覆盖不到 |
| 离线全知上限 | 500bin固定需求下,忽略电量约束的理论上限为R=100%(fleet=12000/7500/4500场景均如此,fleet=4500差距仅0.0002%) |
| 滚动LP稳健性(6场景) | LP在全部场景中R\*提升2.29-4.43pp、空载里程降2.6-9.9%、反应式调度降28.9-84.7%(均值53.3%),无一例外 |
| H=8 vs H=12(固定需求) | ΔR\*均值+0.56pp,范围+0.26~+0.80pp,耗时增加约8-9%——未达"显著更好"门槛,选H=8 |
| H=8 vs H=12(完整均衡) | H=8三布局全部干净收敛;H=12下Oracle和threshold均跑满12轮未收敛(等待时间持续震荡)——进一步确认H=8是更稳健的工程配置 |

## 六、这是否是一个完整的实验流程?

**核心实验问题——"修复后三布局跌破95%,能否用更好的再平衡机制解决"——已经完整、
严谨地回答:能,LP让三布局全部重新可行,且这个结论已经过5+1个固定需求场景、

但"完整项目"意义上,还有第四节列出的5项收尾工作(尤其是默认机制切换的决定、

后续维护者正确理解和复用。
